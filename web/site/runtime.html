Scheduling and replay

The opening chapter compares five kinds of wait. Here we follow the dependencies: which jobs can overlap, which saved answers remain valid, and what must run again after an input changes.

Wall time is what you wait from start to finish. Adding operation durations gives a different number when work overlaps. In one retained build, 180 preparation processes sum to 9.34 hours inside a roughly 5.03-hour span, with up to seven running together. That build was partly cached and interrupted—not a successful cold run of the full corpus. Explore the recorded timeline · Exact intervals.

Component boundaries · dependency explanation, not a new execution

These boundaries let us work on the parts separately. Improve the embedding recipe without rewriting the source reader. Replace the judge without extracting the whole repository again. The changed part’s inputs and outputs must stay explicit; a language feature alone does not arrange this reuse.

This saves file extraction, not every later calculation. The changed repository still needs its references resolved and structural questions evaluated. Adding a definition can change how a name resolves somewhere else. Incremental reuse is smaller than “the whole repository is cached.”

Inside one calculation, two routes can also reach the same set and ask the same next question. The second can use the first answer. Watch that exact-question reuse. A similar-looking answer is not enough.

Different jobs need different machinery

A GPU is good at many similar numerical operations together, as in model inference. A CPU runs general-purpose work: reading files, executing tools and matching table rows. Moving data and waiting for services take time too. The model is one part of the job.

That is what we admire in Modular and Mojo: making CPU and GPU work parts of one program, so each can run where it fits. Attune uses Flix and Bazel, not Mojo’s runtime. The inspiration is to make the parts visible enough to improve separately. Our hosted-model receipts do not identify the provider’s actual hardware.

Flix helps distinguish a calculation on supplied numbers from a request for outside work. The effects example shows that handoff. Bazel handles a larger boundary: which whole steps can run, and which outputs are already valid?

What Bazel needs to know

Bazel is a build system. Tell it which files a step reads and writes; it can track what depends on what. Independent steps can run together. A completed step can be reused when its inputs and execution identity still match.

This actual ranking rule declares the issue vector, the repository’s vector batches and the candidate-list check:

saved file vectors ----+----> rank issue A
                       |       ^
                       |    new issue A vector
                       |
                       +----> rank issue B
                               ^
                            new issue B vector

A batch, or shard, is one separately stored piece of the vectors. Both ranking steps can read it. Flix effects do not create these Bazel dependencies automatically; the rule has to declare them.

Mokhov, Mitchell and Peyton Jones’s Build Systems à la Carte (2018) separates deciding what needs rebuilding from deciding when it can run. That distinction matters here: being reusable and being ready are different questions.

Even instant inference leaves the other required work. That is the intuition behind Amdahl’s law: speeding up one part cannot remove the time spent elsewhere. Gene Amdahl’s original paper (1967).

When many pieces must finish, an unusually slow one can hold up the answer. That long end of the distribution is the tail. Dean and Barroso’s The Tail at Scale (2013) explains the systems problem. Our 42.5-minute extraction process is a concrete reminder: overlap does not make the last required result disappear.

Chang and colleagues’ From LLM Inference to Agentic Workloads (2026) found non-model components dominating latency in five of ten studied agent applications. Raj and colleagues’ A CPU-Centric Perspective (2025; revised 2026) studies CPU/GPU scheduling in agent workloads. Those are external studies, not explanations of this particular Sol run. They motivate timing the whole job.

Save exact repeated work. Overlap independent work. Leave the model a smaller question. The 78× judgment-wait and 28× model-spend comparisons make that worth exploring, without isolating what each engineering choice contributed. And a cheaper answer can still be wrong.
