## ADDED Requirements

### Requirement: Package-local scripts are removed from live workflow surfaces
Package-local scripts SHALL not remain as live public workflow centers,
compatibility shims, invocation pass-throughs, or recipe-owned workflow files
after migration.

#### Scenario: Runtime DB generation stage is migrated
- **WHEN** `packages/trellis/runtime/scripts/generationStage.ts` behavior is
  implemented
- **THEN** DB lifecycle, SQL validation, Kanel generation, SafeQL validation,
  receipt observation projection, and LocalTimescale CLI behavior live under
  typed runtime source modules and recipe invocation paths
- **AND** the package-local script entrypoint is removed after Nx targets and
  tests execute the typed runtime module directly.

#### Scenario: CocoIndex generation stage is migrated
- **WHEN** CocoIndex generation behavior is implemented
- **THEN** behavior moves under `src/internal/generation` or an equivalent typed
  source boundary
- **AND** the package-local script entrypoint is removed after Nx targets and
  tests execute the typed generation module directly
- **AND** generation and freshness behavior emits recipe receipts or planned
  observations.

#### Scenario: Architecture scripts are migrated
- **WHEN** Trellis architecture script behavior is retained
- **THEN** it is represented by Trellis architecture source modules,
  effect-oxlint rules, recipe diagnostics, or recipe-owned Nx targets
- **AND** package-local script entrypoints are removed from active workflow
  paths.

#### Scenario: Fuzzer workflow is retained
- **WHEN** fuzzer campaign behavior remains during migration
- **THEN** campaign behavior is routeable through recipe-backed actions,
  typed modules, and receipts
- **AND** package-local runner scripts are removed from active workflow paths or
  quarantined as historical artifacts with no live adapter path.

#### Scenario: Extensionless package script remains
- **WHEN** any active package keeps a file under `packages/**/scripts/**`,
  including an extensionless shell tool or README/template-like companion
- **THEN** the no-compat validation pass reports the file until the behavior or
  asset is moved into typed source, framework-owned cache/projection output, or
  historical archive outside the active package workflow path.

### Requirement: Generated artifacts have recipe ownership
Generated artifacts SHALL identify a recipe or projection owner before broad
path moves.

#### Scenario: Generated artifact is inspected
- **WHEN** an agent or policy inspects generated-looking files or directories
- **THEN** ownership is visible through recipe `allowedFiles`, output
  descriptors, projection metadata, generated ownership manifests, or
  `@generated by <recipeId>` headers.

#### Scenario: Generated freshness is checked
- **WHEN** generation or freshness validation runs
- **THEN** it emits or plans recipe receipts and observations that explain the
  artifact owner and freshness result.

#### Scenario: Path move is proposed
- **WHEN** a generated artifact path move is proposed
- **THEN** the move occurs only after ownership and freshness receipts can
  explain the artifact.

### Requirement: Tend remains a projection over the shared spine
Tend-specific data SHALL not become an independent ledger when it represents
session, tool, command, long-job, token, or control observations.

#### Scenario: Tend table stores operational state
- **WHEN** Tend stores session, command, long-job, token, or tool facts related
  to recipe-governed work
- **THEN** rows link to recipe ID, run ID, receipt ID, or observation ID where
  relevant
- **AND** Tend is documented as a specialized projection over the shared
  receipt spine.

#### Scenario: Tend linkage is not practical immediately
- **WHEN** direct Tend table widening is not the smallest safe migration step
- **THEN** Tend emits recipe observations as a bridge
- **AND** the migration plan records the remaining linkage debt.

### Requirement: Raw database access stays in runtime boundaries
Product packages SHALL use `RecipeReceiptStore`, read models, or typed service
ports instead of raw Postgres clients.

#### Scenario: Product code needs recipe data
- **WHEN** a product or projection package needs recipe receipts, health,
  repairs, diagnostics, metrics, or observations
- **THEN** it uses the shared store/read-model service boundary or a typed
  runtime adapter.

#### Scenario: Runtime adapter needs raw SQL
- **WHEN** Trellis runtime DB adapter or SQL route tooling needs raw SQL or
  Postgres client behavior
- **THEN** the access remains inside reviewed runtime boundary files and tests.

### Requirement: Clean fork removes old compatibility lanes
The clean fork SHALL remove, internalize, archive, or explicitly quarantine old
compatibility surfaces rather than keeping them as active ontology.

#### Scenario: Legacy substrate lane is encountered
- **WHEN** program-index-first public ontology, SQLite, Drizzle, PgTyped,
  package-local generated companions, artifact ownership shards, or custom
  lifecycle machinery appear in active code paths
- **THEN** the migration removes, internalizes, archives, or quarantines them
  with no live adapter path.

#### Scenario: Context system is proposed
- **WHEN** ContextLens, ContextPacket, ContextStore, vector context selection,
  semantic compression, or agent memory is proposed as part of this change
- **THEN** it is rejected or deferred outside this clean fork.

### Requirement: Workspace validation proves the clean fork
The final implementation SHALL validate policy, protocol, runtime, SQL route,
projection, script cleanup, Tend alignment, and target ownership with Nx-owned
commands.

#### Scenario: Final validation runs
- **WHEN** implementation claims completion
- **THEN** it reports the smallest Nx-owned checks proving the changed slices,
  including policy tests, runtime tests, SQL validation, projection conformance,
  Tend tests where touched, and `workspace:policy-fast` or its recipe substrate
  successor.

#### Scenario: Validation cannot run
- **WHEN** a required validation command cannot run in the current environment
- **THEN** the report names the exact command attempted, the reason it failed,
  and the remaining risk.

### Requirement: Workspace validation rejects compatibility shims
The clean fork SHALL include a validation pass that fails live package-local
script files and compatibility shims after their behavior has moved into typed
modules.

#### Scenario: Active package-local script remains
- **WHEN** a package-local script remains under an active workflow path after
  the corresponding typed module and Nx target exist
- **THEN** the workspace validation pass fails even if the script only forwards
  arguments to the typed module.

#### Scenario: Active package-local script file exists
- **WHEN** any file exists under `packages/<scope>/<package>/scripts/**` or
  `packages/<package>/scripts/**` for an active package
- **THEN** the workspace no-compat validation pass fails unless the file has
  been moved to a non-active historical archive with no live adapter path.

#### Scenario: Historical script is quarantined
- **WHEN** a historical script must be kept for reference
- **THEN** it is outside active package workflow paths, marked historical or
  archived, and has no live Nx target, recipe, projection, or test adapter path.
