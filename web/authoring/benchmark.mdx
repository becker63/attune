# Find the files. Check the historical fix.

Give a method an issue and the repository **before the fix**. It proposes files to open. Then compare them with the files that actually changed. We did this for **85 issues across 22 repositories**.

<h2 id="benchmark-jev">What if Jev sees every file?</h2>

We tried it in a new run of the current Jev model. **No embeddings, no Atlas, no shortlist.** Jev received the issue text and each eligible file path: 28,370 judgments across the same 85 issues. It never saw the implementation or the historical fix. Files marked Relevant come first; alphabetical path order breaks ties.

<Figure name="benchmark-independent" />

Jev alone finds something in **71/85 issues**, and everything in **46/85**. Qwen’s frozen results are **73/85** and **38/85**. Similar totals hide different discoveries: Jev finds **29 required paths** outside Qwen’s first ten, while Qwen finds **27** outside Jev’s. Even path-word matching finds ten required paths that Jev misses. Neither result contains the other.

This tests whether judgment can operate without the other stages—it can. It does **not** prove that their errors are statistically independent, or that combining the answers would improve a future run. We have not evaluated that combination.

<h2 id="benchmark-metrics">What does a success mean?</h2>

Slide the cutoff below. You are reading farther down the **same saved ranking**, not asking for a better prediction. Each `#` is a file in Greenwood’s historical fix.

<Figure name="benchmark-metrics" />

The `@k` means “look only at the first k returned paths.” A required file at rank 11 is missed at ten, even if the full ranking contains it. These measurements answer different questions:

- **Hit@k — did we find anything?** One if at least one eligible required file appears; zero otherwise.
- **Complete@k — did we find everything?** One only if every eligible required file appears. The canonical Flix name is `FileAcc@k`.
- **Recall@k — how much of the fix did we find?** Recovered required files divided by that task’s required-file count.
- **MRR@k — how early was the first hit?** The reciprocal of its rank: rank one gives 1, rank two gives 1/2. No hit inside k gives zero. The table’s MRR averages this over tasks.

At ten, Greenwood’s Qwen ranking contains five of eight eligible required files. That is a Hit of 1, Complete of 0, Recall of 5/8, and reciprocal rank of 1 because the first file is relevant. Expanding the window to 28 finally includes all eight. No prediction changed; only the cutoff changed.

<details className="technical-reading">
<summary>Read the exact Flix scoring rule</summary>

The evaluator first takes the prediction prefix. Then it keeps the gold paths found in that prefix. `List.memberOf` is an exact path-membership check: a plausible filename or a neighboring file does not earn partial credit for that path.

<FlixBlock name="metricGold" />

Hit asks whether that recovered list is nonempty. Complete recovery compares its length with the gold list’s length. Here is the actual complete-recovery rule; `not List.isEmpty(gold)` prevents an empty label from becoming a vacuous success.

<FlixBlock name="metricComplete" />

Ineligible tasks are excluded before aggregation. An eligible task with an abstention or a failed prediction stays in the denominator and receives zero. Also, a ten-path answer cannot completely recover a task with more than ten required files; two tasks in this cohort cross that bound.

</details>

<h2 id="benchmark-structure">What does Atlas do without embeddings?</h2>

Start with words in the issue, and use **no model calls**. P matches those words against paths. P+A also recognizes named files or functions—starting clues called **anchors**. P+A+F adds direct connections. P+A+D also uses Theory’s saved relationship answers.

<Figure name="benchmark-structure" />

At ten files, the path-only method finds something in **30/85** issues. Named starting points raise that to **35/85**, a net gain of five issues. The full structural method also finds **35/85**, and recovers every required file in **18/85**, compared with **14/85** for paths alone. At rank one, anchors raise hits from 10 to 16; adding the later structural scores reduces that count. Structure is useful here, but more structural scoring is not automatically better.

This is structure **without models**, not without a starting clue. Preparing the source facts still costs time.

The [architecture census](#patterns) helps explain why a repository can have rich, recognizable structure without an equally strong localization signal. Common utilities serve many behaviors, public entry points hide implementation files, and dynamic dependencies can escape the recorded relationships. These are source-grounded explanations to investigate, not a causal test proving why the aggregate gain is small.

## Path-word matching: the baseline you can calculate yourself

Could we do this with word matching alone? **P** compares the issue with each file’s **path**—its filename and folders. It never reads the implementation. Try this small example:

<Figure name="reading-path-words" />

Lowercase, split into word-like pieces, discard pieces shorter than three characters, and remove repeats. Count the whole words shared with the issue. Put larger counts first; break ties by the original path. These pieces are called **tokens**, but they are not model billing tokens.

The small trap: `receipt_total` stays one word, and `receiptTotal` becomes `receipttotal`. Neither splits into `receipt` and `total`. A separator is anything except a letter, digit or underscore.

<FlixBlock name="pathScore" />

`pathTokens` is the path’s word list. `foldLeft` starts at zero and visits the issue words: add one if the word is present, otherwise keep the count. The score is a count, not a probability. There is no stemming, semantic similarity, learned weight or hidden inference call.

<details className="technical-reading">
<summary>Read the exact tokenizer</summary>

<FlixBlock name="pathTokens" />

The code uses `Char.isLetterOrDigit`, including Unicode letters; the old ASCII-only comment is narrower than the implementation. `c :: rest` separates the next character from the rest of the list; `Nil` ends it. Accepted characters extend `current`. A separator finishes that piece and starts another. The final filter keeps pieces of length at least three, and `distinct` removes repeats. [The ordering key](sources/path-order.flix) reverses score order and then uses the path to break ties.

</details>

P misses behavior whose name is absent from the path. Qwen also sees source text. **P and Q are alternative starting rankings**, not two steps in sequence. Beating P means beating this simple rule, not every possible word-search method.

<h2 id="benchmark-bm25">BM25: a measured comparison on one issue</h2>

BM25 searches for the issue’s words in file paths and source text. Matching a term that appears in few files contributes more; term frequency and document length also affect the score. The retained Greenwood recording compares BM25 and Qwen on exactly the same 393 candidate paths. This is an existing recording, not a new model run.

<Figure name="benchmark-bm25" />

Qwen puts five of the eight fixing files in the first ten; BM25 puts three there. But BM25 ranks the shared `resource-utils.js` helper at 11, ahead of Qwen’s 24. That counterexample is useful: the embedding improves several ranks without improving every rank. Neither method recovers the whole fix at ten in this recording.

BM25’s one-issue result is not P’s **30/85** cohort score. Different method, different evidence.

<h2 id="benchmark-sol">What did Sol actually do?</h2>

The frontier comparison uses `gpt-6.1-sol` at medium effort. The original and inspected runs are distinct frozen arms. The original run observed no tool calls and often abstained; treating it as a strong repository-reading baseline would be misleading. The inspected run explicitly required searching and reading implementation files before returning up to ten existing paths.

<BenchmarkProtocols />

Both Sol procedures were one bounded turn per task. They saw the public issue and clean repository, with the historical labels withheld. The inspected run returned a mean of 3.23 paths across 88 turns, rather than a complete candidate ranking. Its prompt asked it to avoid padding an answer. A ten-position scoring window is therefore not the same thing as ten returned predictions.

## The preparation bill is not just inference

The source reader recognizes definitions, imports and calls; Flix checks their targets. In the recorded build, the longest extraction process took **42.5 minutes**. A fast judgment on prepared data does not erase that cost. [Replay all 92 extraction actions and inspect their timing distribution](#extraction).

## What we learned—and what we did not

Learned retrieval is strong in this panel. Narrow judgment improves its ordering, and structural context adds a smaller aggregate improvement with individual regressions. Sol’s different procedure recovers issues that the ranked pipeline misses. None of these observations establishes general model superiority, causal credit for a particular Atlas operator, or performance on an unseen architectural population.

The benchmark labels are change-path labels, not a manually verified minimum explanation. New files, unsupported source and tests can matter to a real fix while being ineligible here. Source names and code snippets in an issue can make retrieval easier. These limits are part of the problem being measured, not footnotes to remove from the denominator.
