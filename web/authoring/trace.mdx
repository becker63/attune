# BM25 beside Attune

One issue. The same 393 files. Two ways to find an implementation.

This is a **saved comparison on a known historical case**, separate from the frozen benchmark. When recorded, BM25 searched locally and Qwen obtained fresh embeddings; Flix ranked them. Atlas reused the pinned version’s facts and structural answers. No fixing paths entered those steps, and no model is running now.

BM25 searches file paths and full source text. It rewards matching terms that are rarer across the candidate files, with a length adjustment. Qwen embeds the issue and raw file contents, then compares their vectors. The two methods use the same candidate files but deliberately different representations.

## Time is part of the mechanism

<TraceTiming />

The Qwen acquisition process includes request waiting and fixture materialization. The Flix rank stage includes compiler/launcher startup as well as ranking; its own test output separately reports the body duration. Atlas metadata assembly reads retained facts and witnesses—it does not measure source extraction or Theory matching from scratch. The recording includes manual setup gaps, so stage durations are not an uninterrupted end-to-end benchmark.

BM25 is much cheaper to start here. Qwen's opportunity is to reuse file vectors for later issues. This recording does not measure a warm online query, and it does not establish that extra latency pays off across repositories.

## Check the historical fix afterward

<TraceReveal />

This recording uses an explicit BM25 baseline: lowercase ASCII alphanumeric tokens over path plus source, unique query terms, no stemming or stop-word filter, `k1 = 1.2`, `b = 0.75`, score descending with path ascending for ties. It is not the census's path-token P arm. Qwen retains its original prefix, truncation and 4,096-dimensional recipe. This familiar example is explanatory, not held-out evidence.
