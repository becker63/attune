## The common vocabulary

A **file** is a source path. A **symbol** is a named definition, such as a function. Grit extracts definitions, imports and calls. Flix admits justified targets, then reverses those same pairs to provide three backward directions. They are not six independent measurements.

<Figure name="datalog-pipeline" />

Starting from a symbol, `DefinedIn` finds its file; `ImportedBy` finds that file’s users. A sequence of such lookups is a route. Each operation accepts files or symbols and returns a new set of the declared type.

### Theory: write a small question as data

Once “who shares a dependency?” works, we can ask nearby questions: who calls a name defined here? Which file contains the thing that this function calls? Each question rearranges a few of the same relationship lookups.

`Attune.Theory` writes these little questions down as data. A **descriptor** is a recipe with three fields. `atoms` lists the required relationships. `denied` lists pairs of positions that must hold different values. `outputs` lists which positions to return. The evaluator can read many such recipes without generating a new source file for each one.

The supported grammar permits one to three positive two-ended relationships, up to four typed positions, one or two output positions, and an optional inequality. “Positive” means requiring a fact to exist. The relationships must connect, and every returned position must occur in a relationship. These limits make a finite, inspectable family; they do not amount to unrestricted rule generation.

The following descriptors were checked and executed through the current Theory implementation on tiny authored facts. A numbered **position** is just a blank to fill, like `a`, `b` or `center` in the shop rule. Position 0 does not mean “the first file in the repository.” It means “the first named place in this question.”

The braces hold a **record**: named fields grouped into one value. `outputs = 0 :: 1 :: Nil` says “return position 0, followed by position 1, then end the list.” `::` builds a list and `Nil` is the empty list at its end. `denied = Nil` says there are no pairs required to differ. For comparison, `denied = (0, 2) :: Nil` would require the values at positions 0 and 2 to differ. That is the descriptor’s counterpart of `a != b`.

Read the diagrams first, then the comments. They describe the same small operation.

### Match the recipe against the facts

There are two tables to read. The **recipe table**, called `Desc`, says which relationships the question requires. The **fact table**, called `Edge`, says which relationships actually exist in the world. The engine must find facts that satisfy the recipe.

Take the two-import question. The recipe says: find an Imports row from position 0 to position 1, then another Imports row from position 2 to that **same position 1**. The actual file names fill those positions. A successful filling is called a **binding**—nothing more mysterious than names assigned to the blanks.

The code below is the real shared-target rule, with explanatory comments added. Instead of hardcoding Imports, it reads `r0` and `r1`, the two relationship names, from the recipe. That lets the same checked rule handle other compatible pairs of relationships.

<DatalogCode name="bindingNotes" />

`Binding(...)` is the row we want to produce. `Desc(...)` reads the recipe. The two `Edge(...)` lines find its supporting facts. Because both repeat `w` and `e1`, they must agree on the world and shared target. The `shape` string chooses this arrangement of arrows: 0 → 1 and 2 → 1.

The final three lines implement the optional “these positions must be different” conditions. Each line allows a match if that pair was not constrained, or if its two values really differ. In the frozen 72-question family no inequality was requested, so these checks do not remove self-pairs.

There is one bookkeeping detail: the stored binding reserves four positions for all supported question shapes. This shape needs only three, so its last `e0` is filler. It is not an additional source relationship. The underscores `_` mean “this rule does not need this column.”

Once a binding exists, we still have to decide what to return. In the shared-dependency example, we might want both consumers, or only the shared target. The input facts can be identical while the requested answer differs.

## Reuse the expensive answer; ask a new small question

The source world and structural question determine the matched rows. The wording of a new issue does not change those rows. We can therefore keep the world’s prepared answers and select the ones useful for a new candidate, instead of repeating the full structural calculation for every issue.

Theory makes this split explicit. `Output` is the prepared answer table. `Anchor` names an item we want to focus on. This actual rule selects prepared rows whose first output matches that item:

<FlixBlock name="anchorOnly" />

Read it as “return this task-specific row if it is already an Output row, and its first item is an Anchor in the same world.” `c` keeps the question’s identity; `w` keeps the world’s identity. This is a lookup into answers already computed. It does not rerun the source reader or reconstruct the relationships.

The frozen Jev prompt writer performs its own bounded lookup against retained answers, using the candidate’s defined symbols. The rule above shows Theory’s explicit reuse boundary; it is not a claim that the Java writer invokes that exact Flix rule for each note.

There is also reuse *inside* a route. Two different sequences of lookups can reach the same exact set. If they ask the same next question in the same world and scope, that calculation can be shared. [The architecture page compares this with prefix caching and shows the actual key](#patterns).

These properties have three different payoffs. **For localization**, source connections add evidence about a candidate’s role. **For wall time**, retained facts and answers avoid repeating preparation, while unchanged file acquisitions can survive a source edit. **For architecture**, the same fixed questions produce different patterns of empty answers and repeated calculations across repositories. None of these observations alone establishes the other two. A cheaply reused empty answer can describe the graph accurately while providing no clue to a fix.

## What about rules that keep going?

So far, our rules make a bounded number of lookups. **Recursion** means a rule can use results produced by that same relationship. Imagine a screen importing a formatter, which imports a units helper:

<pre className="pattern-diagram">{"[screen] --Imports--> [format] --Imports--> [units]\n    |                                        ^\n    `--------------- Reaches ----------------'"}</pre>

<DatalogCode name="recursion" />

The first rule turns direct imports into reachability. The second extends a known path by one import. Evaluation repeats until no new rows appear—a **fixpoint**. This separate, executed teaching example returns the two direct connections and `screen → units`. It is not a claim that the frozen Theory study generated recursive queries.

Datalog has costs: finding matches, storing intermediate values and updating results after changes all take work. Zhao and colleagues’ [*FlowLog: Efficient and Extensible Datalog via Incrementality* (2025 preprint; VLDB 2026)](https://arxiv.org/abs/2511.00865) studies another engine that reuses relational work as inputs change. It is relevant research, not Attune’s implementation or a measured Attune speedup.
